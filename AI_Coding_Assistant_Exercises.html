COMPANION TO THE 32-SLIDE COMIC WORKSHOP

Your AI sidekick.
Your engineering evidence.

28 ready-to-use activities with supplied materials, prompts, expected outputs and facilitator answers.

Created 7 October 2026. The coding sandbox uses only Python’s standard library. All payment effects, accounts, usage logs, rates and model trials are simulated.

Start in five minutes

  1. Extract AI_Coding_Assistant_Exercise_Kit.zip and open its folder in your approved IDE.
  2. Use Python 3.10 or later. No package installation is needed.
  3. Run python run_checks.py baseline. Expected: three passing tests.
  4. Run python run_checks.py contract. Expected: three intentional failures on the starter.
  5. Keep facilitator/ outside participant context until debrief. The full fix should pass python run_checks.py all.

Substitute python3 if that is your system’s Python command. Extract a fresh copy for independent coding exercises. Cloud agents require an approved repository setup. Swarm activities also work with separate chats or human role groups.

Facilitator reference: python run_checks.py all --solution runs the six checks against the supplied reference, without overwriting the learner code.

Session routes

One-hour route: setup (5), Activities 1 (4), 4 (5), 8 (4), 12 (7), 19 (6), 24 (8), 26 (8), 27 (5), and discussion (8). Treat omitted activities as follow-up practice.

Full lab: all 28 activities total 151 minutes of suggested activity time, plus setup, breaks and discussion. Split across several sessions if participants implement each coding task.

Written-only option: use briefs, plans, supplied logs, calculations and tabletop reviews. Discuss the provided test outputs without running an IDE agent.

The exercise implementation is a small Python service. Deck examples involving FastAPI, HTTP 409 or pytest are illustrative. Here a changed payload raises Conflict, and tests use unittest. The memory repository and thread tests do not prove multi-process or production payment safety.

ACTIVITY 01 · SLIDES 1, 30 · 4 MINUTES

Who owns the generated change?

Ready-to-use material

Pair activity. Give participants this claim: “The assistant says all tests pass, so we can merge.” Use the baseline starter and its three green sanity tests.

Run the exercise

  1. Run python run_checks.py baseline.
  2. List five pieces of evidence you would request before keeping the change.
  3. Compare your list with a partner and identify one guarantee the current tests do not provide.

Prompt to paste

Inspect payments/service.py and tests/test_baseline.py. Do not edit files. Explain what the current tests prove, what they do not prove, and which evidence a human reviewer needs before accepting a payment retry fix. Do not inspect facilitator/.

Expected participant output

A short acceptance checklist grounded in this repository, rather than a confident yes/no verdict.

Success check

Participant explicitly distinguishes a passing sanity suite from the full contract and can name an untested failure scenario.

Facilitator answer and debrief

The baseline proves a simple charge, sequential same-payload reuse and negative-amount rejection. It does not cover conflicting payloads, concurrent calls or timeout ambiguity. Ask for the actual diff, contract regressions, command output, affected callers and unverified limitations. A human decides whether the evidence is sufficient.

ACTIVITY 02 · SLIDES 2 · 6 MINUTES

The giant task versus the bounded task

Ready-to-use material

Extract two fresh starter copies. Copy A gets a vague brief. Copy B gets a bounded brief. Give each assistant a two-minute observation budget, then pause it.

Run the exercise

  1. In A, ask “Fix retries and make everything production ready.”
  2. In B, use the working prompt below.
  3. Compare assumptions, planned files and actual diff size. Do not merge either result.

Prompt to paste

Fix only changed-payload handling in PaymentService.pay. Same key with another amount or account must raise payments.repository.Conflict. Preserve the public signature. Add no dependency. Use the existing fingerprint and repository APIs. Add a regression assertion, then run baseline and the changed-payload contract test. Leave concurrency and timeout recovery for later. Do not read facilitator/.

Expected participant output

A bounded patch and relevant test evidence. The other two starter contract failures may remain at this stage.

Success check

No API change or new package. The changed-payload test passes for the intended reason and baseline remains green.

Facilitator answer and debrief

The current code returns an existing receipt without comparing payload_hash. Validate the stored fingerprint before returning. Check both amount and account changes. New frameworks, unrelated formatting and blanket “production ready” claims are scope expansion. The A/B experiment demonstrates differences in outputs, not a statistical productivity result.

ACTIVITY 05 · SLIDES 5 · 7 MINUTES

The idempotency truth table

Ready-to-use material

Use the workshop contract. Present five requests: K1/10000/DEMO-A; repeat it; K1/15000/DEMO-A; two simultaneous K2/10000/DEMO-A; K3 timeout after charge then retry.

Run the exercise

  1. Predict the receipt, conflict or unknown outcome for each request.
  2. Run baseline and contract suites.
  3. Match each intentional failure to the contract row it violates.
  4. Explain why increasing a retry count cannot resolve an unknown provider outcome.

Prompt to paste

Build a truth table for the five request scenarios in this exercise using materials/contract.md. Then inspect the starter and map each contract violation to a specific code path. Do not edit. Distinguish local record state from provider charge state.

Expected participant output

A five-row behavior table and a mapping to the three failing regression tests.

Success check

The participant states that a timeout does not establish that the charge failed.

Facilitator answer and debrief

The first request charges once. An identical repeat returns the same receipt. A changed payload raises Conflict and adds no charge. Concurrent same-key requests share one charge. The first timeout raises OutcomeUnknown, but the provider already charged; the next retry reconciles to that receipt. Starter violations are ignored payload changes, a fresh provider key per attempt and no unknown-outcome recovery.

Ready-to-use material

Run the exercise

Prompt to paste

Expected participant output

Red, green, and the misleading test

Ready-to-use material

Compare this weak assertion with the contract test: “assert receipt is not None” after two concurrent calls.

Run the exercise

  1. Run python run_checks.py contract on fresh starter code.
  2. Read the concurrency assertions and explain why the weak assertion passes despite the bug.
  3. Add or improve one assertion, then rerun it.
  4. After implementing a fix, keep the same expected behavior and show green.

Prompt to paste

Review test_concurrent_retries_create_one_charge. Explain why returning any receipt is insufficient. Preserve the deterministic Barrier and assert both one provider charge and identical charge IDs. Show the starter failure before changing the implementation. Do not weaken assertions, remove the scheduling seam or inspect facilitator/.

Expected participant output

Evidence that the regression fails on the starter for duplicate effects, then passes after the intended fix.

Success check

Facilitator answer and debrief

Import errors, deadlocked fixtures, skipped tests or relaxed assertions do not qualify as a correct red-to-green result.
